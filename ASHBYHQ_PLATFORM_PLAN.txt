1. HARD CONSTRAINTS (UNCHANGED FROM v2 UNLESS MARKED)
====================================================================
- Pure JavaScript, Node ESM. Base layer (ashby-hybrid-automation.js
  engine) untouched at workspace root; platform lives entirely in
  ashbyhq-dashboard/ (folder isolation is a rule).
- 100% LOCAL. Server binds 127.0.0.1:3100. No cloud, no Supabase.
- NO resume storage by us. applicants.resume_address only.
- CA is the decision start point: APPLY or SKIP(reason). Nothing
  runs before a CA clicks APPLY.
- [CHANGED v3.1] Job links arrive from the external DB as
  (AWL-ID -> url) pairs and sit in applicant_joblinks until the
  CAM assigns the applicant; only then do they MATERIALISE into
  ASSIGNED applications. No manual add-link UI yet.
- [CHANGED v3.1] Applicant -> CA attachment is a CAM action,
  capped by a per-CAM applicant_quota only DEV may raise. AM
  remains data-only (ams table shown on cards; no login).
- [NEW v3.1] Concurrency is bounded ONLY by MAX_CONCURRENT_RUNS
  (host RAM/CPU); within the cap every run is its own spawned
  browser child process - no queue ordering, no shared state,
  no engine modifications.
- [NEW v3.1] The resume file is downloaded per run to
  data/runs/<run-id>/ and DELETED on close - we still store only
  the address.
- [CHANGED] Auth now exists, but codes go to the CONSOLE (stub),
  there are no passwords, and accounts self-create at sign-up.
- [NEW] CAM overrides: a CAM can reassign CA and force ANY status
  (bypassing the state machine) inside their own tree, reason
  mandatory, every override audited in application_events.
- [NEW v3.2] DEV CAM re-assignment of a CA is confirm-gated in
  the UI (pending indicator + checkbox + Save). The API itself
  stays a plain DEV endpoint - trust-but-confirm is a UI rule.

2. AUTH FLOW (WHAT / HOW / WHY)
====================================================================
 Step 1  POST /api/auth/request-code {email, name?, role?, managerId?}
   - Existing email  -> SIGN-IN. Role comes from the staff record.
     The dropdown is IGNORED (the sign-in screen now says so:
     "Existing <ROLE> account - the role is fixed at sign-up").
   - New email       -> SIGN-UP with the chosen role.
     CA requires selecting an existing CAM (400 otherwise).
     CAM/DEV need no manager.
   - Issues 6-digit code (5-min TTL, max 5 wrong attempts,
     single active code per email via upsert), prints it through
     core/mailer.js stub.
 Step 2  POST /api/auth/verify-code {email, code}
   - Correct code -> row deleted (single use) -> session token
     (uuid) stored in sessions table, 12h TTL -> returned to the
     browser which keeps it in localStorage('awl_token').
 Step 3  Every /api/* call sends "Authorization: Bearer <token>";
   server resolves it to the staff row; expired/invalid -> 401 ->
   client clears token and redirects to sign-in.

 WHY: proves the full identity->role->scoped-dashboard pipeline
 without passwords; swapping in a real mail sender later = edit
 ONE function in core/mailer.js. Restriction: an email can never
 change role after creation (no role-change UI yet, even for DEV).

3. STATE MACHINE + WHO MAY DO WHAT
====================================================================
 ASSIGNED -> QUEUED            CA APPLY (owner only) | CAM/DEV apply
 ASSIGNED -> FAILED            CA SKIP+reason (owner) | CAM/DEV
 QUEUED   -> APPLYING          worker claim (claimForRun atomic,
                               v3.1 - guarded UPDATE, run_id+attempts)
 QUEUED   -> FAILED            DEV force-fail
 APPLYING -> SUCCESS/PENDING/FAILED   worker result mapping (v3.1:
                               engine jobs/*.json status -> state)
 PENDING  -> SUCCESS/FAILED    DEV resolve
 FAILED   -> QUEUED            DEV re-queue only
 SUCCESS  -> (terminal)

 transition() in db/store.js enforces edges (Illegal transition
 errors are returned, not silently ignored) AND writes an
 application_events row per change.

 ROLE / PERMISSION MATRIX (all enforced server-side, not just UI):
 CA   sees+acts: own applications (ca_id = me). APPLY/SKIP on own
      ASSIGNED rows. Applicants attached to me (card shows AM name +
      "under CAM X" as info only).
 CAM  sees: entire tree (denormalized manager_id on every app row).
      acts: APPLY/SKIP anywhere in tree, CA Overview drill-down,
      Job Links matrix, REASSIGN CA (tree-only - cross-tree blocked
      400/403), FORCE STATUS any->any (reason required, audited),
      [v3.1] ASSIGN applicants from their pool to a CA - quota-
      capped (assigned >= quota -> 400), which materialises that
      applicant's pending job links into ASSIGNED applications.
      cannot: see another CAM's tree, reassign to another tree's CA,
      raise their own quota.
 DEV  sees: everything, everyone. Acts: all CA/CAM powers +
      re-queue / force-fail / resolve PENDING, worker enable/disable
      (+ live active/maxConcurrent readout), [v3.1] Postgres sync,
      single-doc JSON ingest, per-CAM applicant_quota setting,
      [v3.2] CA -> CAM re-assignment via the confirm-gated Staff
      tab, raw table inspector (whitelisted tables, read-only),
      full event stream.
 WORKER (v3.1, actor 'worker'): claim QUEUED -> APPLYING, map run
      outcome -> SUCCESS/PENDING/FAILED, crash -> FAILED. Only runs
      while system_state.worker_enabled = 'true'.
 AM   no login, no actions - linkage data only.

 WHY denormalized ca_id/manager_id on applications: one WHERE
 clause per role scope, no recursive joins, scoping cannot leak.
 WHY CAM force-status bypasses the machine: ops reality - a CAM
 may know a recruiter confirmed receipt (ASSIGNED->SUCCESS); the
 mandatory reason + cam_force_status event keeps it accountable.

4. DATA MODEL (db/schema.sql - actual, applied on boot)
====================================================================
 staff(uuid PK, email UNIQUE, name, role CHECK ca|cam|dev,
       manager_id ->staff.uuid NULL,
       applicant_quota INT DEFAULT 25,  -- v3.1 per-CAM cap DEV sets
       ext_id,                          -- v3.1 external Postgres staff uuid
       active, last_sign_in, created_at)
 ams(uuid PK, name, email)
 otp_codes(email PK, code, expires_at, attempts, created_at)
 sessions(token PK, staff_uuid, created_at, expires_at)
 job_links(id PK AUTO, company, title, url UNIQUE, url_hash,
           link_status valid|expired|already_applied, seeded_at)
 applicants(awl_id PK, full_name, email, phone, am_id,
            ca_id,        -- set by the CAM since v3.1 (was AM-side)
            cam_id,       -- v3.1 owning CAM whose pool it sits in
            ext_id,       -- v3.1 external client UUID from Postgres
            assigned_at,  -- v3.1 when a CA was attached
            resume_address, profile_json, source_updated_at)
 applicant_joblinks(id PK, awl_id, url, company, title,
            materialized 0|1, added_at)   -- v3.1
            -- (AWL-ID -> link) pairs streamed from the external DB;
            -- stay pending until the CAM assigns, then materialise
            -- into ASSIGNED applications (section 9)
 applications(id PK, awl_id, link_id, ca_id, manager_id,
   status ASSIGNED|QUEUED|APPLYING|SUCCESS|PENDING|FAILED
   (state machine enforced in store.js, not by SQL CHECK),
   skip_reason, fail_reason, run_id, attempts,
   screenshot_path, resolution_log_json,  -- v3.1 worker outputs
   decision_by, decision_at, queued_at, finished_at,
   created_at, updated_at, UNIQUE(awl_id, link_id))
 application_events(id, application_id NULL, type, actor,
           payload_json, ts)          -- audit spine for all actions
 system_state(key PK, value, updated_at)  -- worker_enabled etc.
 Indexes: applications(ca_id,status), (manager_id,status),
 applicants(ca_id), events(application_id),
 applicant_joblinks(awl_id, materialized)  -- v3.1 pending scan

 migrate() = schema.sql PLUS idempotent ensureColumn() ALTERs
 (v3.1): an existing app.db upgrades in place - no data reset
 needed between versions. New tables ride CREATE IF NOT EXISTS.
 Restriction: readTable() exposes only a whitelist (now including
 applicant_joblinks) and only to DEV.

7. ARCHITECTURE DECISIONS RECAP (WHY IT IS THIS WAY)
====================================================================
 1. node:sqlite over better-sqlite3: no native compile on Windows,
    sync API simplifies all store code.
 2. Denormalized ca_id/manager_id per application: single-clause
    scoping; reassign updates them explicitly (and optionally the
    whole applicant).
 3. State machine + explicit override lane: normal flow stays
    safe/legal; CAM/DEV overrides exist but are reason-required
    and event-tagged, so audits can always tell machine-path vs
    human-override.
 4. One store.js for logic, thin routes: the worker (v3.1) imports
    these same functions (claim + transition + logEvent) -
    no HTTP loopback, no duplicated rules.
 5. UI without framework/build: skeleton stage stays inspectable
    and dependency-free; class-name contract keeps restyling free.
 6. Server-side filtering only: the browser can't request
    out-of-scope rows even by hand-crafting URLs - scope is a
    property of the token, not of the query.
 7. [v3.1] SPAWN, don't refactor: concurrency was asked for
    without touching the proven engine -> one child process per
    run with isolated APPLICANT_DATA_DIR. Free parallelism, zero
    regression risk. (Full rationale: section 9.)
 8. [v3.1] Deferred materialisation: DB job links wait in
    applicant_joblinks and only become applications when the CAM
    assigns. Keeps "nothing exists before a CA decision" true,
    lets quota govern real workload, and a link added to an
    already-assigned applicant materialises immediately.
 9. [v3.2] Destructive re-assignment is confirm-gated in the UI:
    silently saving dropdown edits risks accidental tree moves;
    an explicit old -> new indicator + checkbox makes intent (and
    the audit trail) unambiguous while the API stays simple.

9. v3.1 - EXTERNAL DB + CAM ASSIGNMENT + PARALLEL AUTOMATION
====================================================================
WHAT IT DOES
 The single source of truth for WHO exists and WHAT to apply for is
 now the Azure Postgres DB (viewable in pgAdmin): each applicant is
 an AWL-ID row, and job links are (AWL-ID -> url) pairs. The AM no
 longer assigns CAs - the CAM does, from a quota WE set per CAM.
 Automation starts the instant a CA clicks APPLY and runs every
 application in its OWN browser, concurrently, for any number of
 CAs x applicants - no queue, no sequence.

DATA FLOW (verified end-to-end, 10/10)
 1. connector/applicant-db.js pulls applicants (+ optional link
    pairs) from Postgres via syncFromPostgres(), or ingestDocument()
    loads one exported { client, additional_information } JSON. Both
    call mapApplicantDoc() which normalises the demographic payload
    into the exact profile shape the base engine already consumes and
    stores ONLY the resume S3 address, never the file.
 2. Applicants land in the OWNING CAM's pool with ca_id = NULL
    (cam_id from client.careerassociatemanagerid via staff.ext_id,
    or a CAM picked in the DEV UI). Links wait in applicant_joblinks
    with materialized = 0.
 3. CAM "Assignments" tab (GET /api/cam/pool) shows the pool + live
    quota (assigned/quota). CAM picks a CA -> POST /api/cam/assign
    -> assignApplicantToCa() enforces the quota, sets ca_id/cam_id,
    and materializeJoblinks() turns each pending link into an
    ASSIGNED application in that CA's queue.
 4. CA clicks APPLY -> application ASSIGNED -> QUEUED, and
    worker.kick() runs immediately (no poll wait).

PARALLELISM MODEL (the core of the request)
 worker/runner.js keeps a poll loop (WORKER_POLL_MS) that is a
 backstop; the real trigger is server.js calling worker.kick() on
 every APPLY. tick() claims up to (MAX_CONCURRENT - active) QUEUED
 rows and, for EACH, spawn()s an independent child:
     node ashby-hybrid-automation.js <url> <resume> 
       env APPLICANT_ID / PERSON_PROFILE_PATH / APPLICANT_DB_PATH /
           APPLICANT_DATA_DIR=<own run dir>
 N children = N browsers at once, each with its own applicant-data
 folder, so there is NO shared state and NO ordering. claimForRun()
 flips QUEUED -> APPLYING atomically (guarded UPDATE) so two slots
 can never grab the same row. QUEUED rows past the cap simply wait
 for the next free slot and are still picked up live. On child close
 readLatestResult() scans the run's jobs/*.json and finishRun() maps
 success->SUCCESS, failed->FAILED (banner reason), unknown/manual-
 review/pending->PENDING, crash/no-result->FAILED; the downloaded
 resume is then deleted.

NEW SCHEMA (idempotent ALTERs in db/index.js migrate())
 staff: applicant_quota (default 25, the per-CAM cap), ext_id
 applicants: cam_id, ext_id, assigned_at (ca_id now set by CAM)
 new table applicant_joblinks (awl_id,url,company,title,materialized)
 applications: resolution_log_json

NEW / CHANGED ROUTES (server.js)
 GET  /api/cam/pool            pool + quota usage + the CAM's CAs
 POST /api/cam/assign          attach applicant to a CA (quota-checked)
 POST /api/dev/sync            pull applicants+links from Postgres
 POST /api/dev/ingest          load one demographic JSON export
 POST /api/dev/staff/:uuid/quota   set a CAM's applicant quota
 POST /api/dev/worker            enable/disable the runner (was toggle)
 APPLY route now also calls worker.kick()

NEW UI (public/js/app.js)
 CAM -> "Assignments" tab (quota banner + per-applicant CA picker)
 DEV -> "Data Sync" tab (Sync from Postgres, Ingest JSON, per-CAM
          quota inputs, worker enable/disable with live active count)

CONFIG (.env.example in dashboards folder)
 WORKER_ENABLED, MAX_CONCURRENT_RUNS, WORKER_POLL_MS, ENGINE_PATH,
 PG_CONNECTION_STRING or PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/
 PGSSL, PG_APPLICANTS_TABLE / PG_APPLICANTS_QUERY / PG_LINKS_QUERY.
 pg is an OPTIONAL dependency (imported lazily) so the server boots
 with the DB unwired.

STILL OPEN (v3.1 edges)
 - Multiple simultaneous HEADED browsers need enough machine RAM /
   CPU; raise MAX_CONCURRENT_RUNS to match the host, or run several
   worker hosts later.
 - Screenshot / resolution_log surfacing in the CA + CAM views.
 - A scheduled/automatic Postgres poll (sync is manual-click today).
 - Real knockout-question answer mapping is limited to the fields
   present in the demographic doc; anything else falls to the

10. v3.2 - DEV STAFF TAB: CONFIRM-GATED CAM CHANGE
====================================================================
WHAT public/js/app.js renderDevStaff() only - no server change.
HOW  Each CA row: dropdown + a "Current CAM: <name>" caption. On
     dropdown change (different value only) an amber dashed
     PENDING box appears: "Change CAM: <old> -> <new>" with a
     checkbox, a Save button DISABLED until the box is ticked, and
     Revert. Only the ticked Save POSTs /api/dev/staff/:uuid/
     manager, then the tab re-renders so the new CAM becomes
     "Current". Picking the original value or Revert hides the box;
     a failed POST rolls back the dropdown and hides the box.
WHY  The old flow saved on every dropdown change - one mis-click
     silently re-parents a CA (changes who sees their whole tree).
     The indicator makes the consequence visible BEFORE it happens.
RESTRICTIONS gate is UI-only by design (the endpoint stays a
     plain DEV route for scripting); applies to CA rows only;
     moving a CA between CAMs does NOT retro-reassign existing
     applications - use the CAM Job Links matrix for that.
