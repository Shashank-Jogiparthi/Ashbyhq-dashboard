1. HARD CONSTRAINTS (UNCHANGED FROM v2 UNLESS MARKED)
====================================================================
- Pure JavaScript, Node ESM. Base layer (ashby-hybrid-automation.js
  engine) untouched at workspace root; platform lives entirely in
  ashbyhq-dashboard/ (folder isolation is a rule).
- 100% LOCAL. Server binds 127.0.0.1:3100. No cloud, no Supabase.
- NO resume storage by us. applicants.resume_address only.
- CA is the decision start point: APPLY or SKIP(reason). Nothing
  runs before a CA clicks APPLY.
- [CHANGED v3.1] Job links arrive from the external DB as
  (AWL-ID -> url) pairs and sit in applicant_joblinks until the
  CAM assigns the applicant; only then do they MATERIALISE into
  ASSIGNED applications. No manual add-link UI yet.
- [CHANGED v3.1] Applicant -> CA attachment is a CAM action,
  capped by a per-CAM applicant_quota only DEV may raise. AM
  remains data-only (ams table shown on cards; no login).
- [NEW v3.1] Concurrency is bounded ONLY by MAX_CONCURRENT_RUNS
  (host RAM/CPU); within the cap every run is its own spawned
  browser child process - no queue ordering, no shared state,
  no engine modifications.
- [NEW v3.1] The resume file is downloaded per run to
  data/runs/<run-id>/ and DELETED on close - we still store only
  the address.
- [CHANGED] Auth now exists, but codes go to the CONSOLE (stub),
  there are no passwords, and accounts self-create at sign-up.
- [NEW] CAM overrides: a CAM can reassign CA and force ANY status
  (bypassing the state machine) inside their own tree, reason
  mandatory, every override audited in application_events.
- [NEW v3.2] DEV CAM re-assignment of a CA is confirm-gated in
  the UI (pending indicator + checkbox + Save). The API itself
  stays a plain DEV endpoint - trust-but-confirm is a UI rule.

2. AUTH FLOW (WHAT / HOW / WHY)
====================================================================
 Step 1  POST /api/auth/request-code {email, mode, role?, managerId?, name?}
   - mode is sent by the portal's two tabs (Sign in / Sign up) and
     defaults to 'signup' for older callers. The tabs are separate
     panels inside one framed card; there is NO name field - the
     display name is derived from the email local part by
     db/store.js displayNameFromEmail().
   - mode=signin + unknown email -> 404 ("switch to Sign up").
     mode=signup + known email -> 409 ("switch to Sign in").
     A sign-in therefore can never create an account and a sign-up
     can never log into one; role always comes from the record.
   - New email (signup) -> SIGN-UP with the chosen role.
     CA requires selecting an existing CAM (400 otherwise).
     CAM/DEV need no manager. ADMIN only bootstraps the first one.
   - Issues 6-digit code (5-min TTL, max 5 wrong attempts,
     single active code per email via upsert), prints it through
     core/mailer.js stub.
 Step 2  POST /api/auth/verify-code {email, code}
   - Correct code -> row deleted (single use) -> session token
     (uuid) stored in sessions table, 12h TTL -> returned to the
     browser which keeps it in localStorage('awl_token').
 Step 3  Every /api/* call sends "Authorization: Bearer <token>";
   server resolves it to the staff row; expired/invalid -> 401 ->
   client clears token and redirects to sign-in.

 WHY: proves the full identity->role->scoped-dashboard pipeline
 without passwords; swapping in a real mail sender later = edit
 ONE function in core/mailer.js. Restriction: an email can never
 change role after creation (no role-change UI yet, even for DEV).

3. STATE MACHINE + WHO MAY DO WHAT
====================================================================
 ASSIGNED -> QUEUED            CA APPLY (owner only) | CAM/DEV apply
 ASSIGNED -> FAILED            CA SKIP+reason (owner) | CAM/DEV
 QUEUED   -> APPLYING          worker claim (claimForRun atomic,
                               v3.1 - guarded UPDATE, run_id+attempts)
 QUEUED   -> FAILED            DEV force-fail
 APPLYING -> SUCCESS/PENDING/FAILED   worker result mapping (v3.1:
                               engine jobs/*.json status -> state)
 PENDING  -> SUCCESS/FAILED    DEV resolve
 FAILED   -> QUEUED            DEV re-queue only
 SUCCESS  -> (terminal)

 transition() in db/store.js enforces edges (Illegal transition
 errors are returned, not silently ignored) AND writes an
 application_events row per change.

 ROLE / PERMISSION MATRIX (all enforced server-side, not just UI):
 CA   sees+acts: own applications (ca_id = me). APPLY/SKIP on own
      ASSIGNED rows. Applicants attached to me (card shows AM name +
      "under CAM X" as info only).
 CAM  sees: entire tree (denormalized manager_id on every app row).
      acts: APPLY/SKIP anywhere in tree, CA Overview drill-down,
      Job Links matrix, REASSIGN CA (tree-only - cross-tree blocked
      400/403), FORCE STATUS any->any (reason required, audited),
      [v3.1] ASSIGN applicants from their pool to a CA - quota-
      capped (assigned >= quota -> 400), which materialises that
      applicant's pending job links into ASSIGNED applications.
      cannot: see another CAM's tree, reassign to another tree's CA,
      raise their own quota.
 DEV  sees: everything, everyone. Acts: all CA/CAM powers +
      re-queue / force-fail / resolve PENDING, worker enable/disable
      (+ live active/maxConcurrent readout), [v3.1] Postgres sync,
      single-doc JSON ingest, per-CAM applicant_quota setting,
      [v3.2] CA -> CAM re-assignment via the confirm-gated Staff
      tab, raw table inspector (whitelisted tables, read-only),
      full event stream.
 WORKER (v3.1, actor 'worker'): claim QUEUED -> APPLYING, map run
      outcome -> SUCCESS/PENDING/FAILED, crash -> FAILED. Only runs
      while system_state.worker_enabled = 'true'.
 AM   no login, no actions - linkage data only.

 WHY denormalized ca_id/manager_id on applications: one WHERE
 clause per role scope, no recursive joins, scoping cannot leak.
 WHY CAM force-status bypasses the machine: ops reality - a CAM
 may know a recruiter confirmed receipt (ASSIGNED->SUCCESS); the
 mandatory reason + cam_force_status event keeps it accountable.

4. DATA MODEL (db/schema.sql - actual, applied on boot)
====================================================================
 staff(uuid PK, email UNIQUE, name, role CHECK ca|cam|dev,
       manager_id ->staff.uuid NULL,
       applicant_quota INT DEFAULT 25,  -- v3.1 per-CAM cap DEV sets
       ext_id,                          -- v3.1 external Postgres staff uuid
       active, last_sign_in, created_at)
 ams(uuid PK, name, email)
 otp_codes(email PK, code, expires_at, attempts, created_at)
 sessions(token PK, staff_uuid, created_at, expires_at)
 job_links(id PK AUTO, company, title, url UNIQUE, url_hash,
           link_status valid|expired|already_applied, seeded_at)
 applicants(awl_id PK, full_name, email, phone, am_id,
            ca_id,        -- set by the CAM since v3.1 (was AM-side)
            cam_id,       -- v3.1 owning CAM whose pool it sits in
            ext_id,       -- v3.1 external client UUID from Postgres
            assigned_at,  -- v3.1 when a CA was attached
            resume_address, profile_json, source_updated_at)
 applicant_joblinks(id PK, awl_id, url, company, title,
            materialized 0|1, added_at)   -- v3.1
            -- (AWL-ID -> link) pairs streamed from the external DB;
            -- stay pending until the CAM assigns, then materialise
            -- into ASSIGNED applications (section 9)
 applications(id PK, awl_id, link_id, ca_id, manager_id,
   status ASSIGNED|QUEUED|APPLYING|SUCCESS|PENDING|FAILED
   (state machine enforced in store.js, not by SQL CHECK),
   skip_reason, fail_reason, run_id, attempts,
   screenshot_path, resolution_log_json,  -- v3.1 worker outputs
   decision_by, decision_at, queued_at, finished_at,
   created_at, updated_at, UNIQUE(awl_id, link_id))
 application_events(id, application_id NULL, type, actor,
           payload_json, ts)          -- audit spine for all actions
 system_state(key PK, value, updated_at)  -- worker_enabled etc.
 Indexes: applications(ca_id,status), (manager_id,status),
 applicants(ca_id), events(application_id),
 applicant_joblinks(awl_id, materialized)  -- v3.1 pending scan

 migrate() = schema.sql PLUS idempotent ensureColumn() ALTERs
 (v3.1): an existing app.db upgrades in place - no data reset
 needed between versions. New tables ride CREATE IF NOT EXISTS.
 Restriction: readTable() exposes only a whitelist (now including
 applicant_joblinks) and only to DEV.

7. ARCHITECTURE DECISIONS RECAP (WHY IT IS THIS WAY)
====================================================================
 1. node:sqlite over better-sqlite3: no native compile on Windows,
    sync API simplifies all store code.
 2. Denormalized ca_id/manager_id per application: single-clause
    scoping; reassign updates them explicitly (and optionally the
    whole applicant).
 3. State machine + explicit override lane: normal flow stays
    safe/legal; CAM/DEV overrides exist but are reason-required
    and event-tagged, so audits can always tell machine-path vs
    human-override.
 4. One store.js for logic, thin routes: the worker (v3.1) imports
    these same functions (claim + transition + logEvent) -
    no HTTP loopback, no duplicated rules.
 5. UI without framework/build: skeleton stage stays inspectable
    and dependency-free; class-name contract keeps restyling free.
 6. Server-side filtering only: the browser can't request
    out-of-scope rows even by hand-crafting URLs - scope is a
    property of the token, not of the query.
 7. [v3.1] SPAWN, don't refactor: concurrency was asked for
    without touching the proven engine -> one child process per
    run with isolated APPLICANT_DATA_DIR. Free parallelism, zero
    regression risk. (Full rationale: section 9.)
 8. [v3.1] Deferred materialisation: DB job links wait in
    applicant_joblinks and only become applications when the CAM
    assigns. Keeps "nothing exists before a CA decision" true,
    lets quota govern real workload, and a link added to an
    already-assigned applicant materialises immediately.
 9. [v3.2] Destructive re-assignment is confirm-gated in the UI:
    silently saving dropdown edits risks accidental tree moves;
    an explicit old -> new indicator + checkbox makes intent (and
    the audit trail) unambiguous while the API stays simple.

9. v3.1 - EXTERNAL DB + CAM ASSIGNMENT + PARALLEL AUTOMATION
====================================================================
WHAT IT DOES
 The single source of truth for WHO exists and WHAT to apply for is
 now the Azure Postgres DB (viewable in pgAdmin): each applicant is
 an AWL-ID row, and job links are (AWL-ID -> url) pairs. The AM no
 longer assigns CAs - the CAM does, from a quota WE set per CAM.
 Automation starts the instant a CA clicks APPLY and runs every
 application in its OWN browser, concurrently, for any number of
 CAs x applicants - no queue, no sequence.

DATA FLOW (verified end-to-end, 10/10)
 1. connector/applicant-db.js pulls applicants (+ optional link
    pairs) from Postgres via syncFromPostgres(), or ingestDocument()
    loads one exported { client, additional_information } JSON. Both
    call mapApplicantDoc() which normalises the demographic payload
    into the exact profile shape the base engine already consumes and
    stores ONLY the resume S3 address, never the file.
 2. Applicants land in the OWNING CAM's pool with ca_id = NULL
    (cam_id from client.careerassociatemanagerid via staff.ext_id,
    or a CAM picked in the DEV UI). Links wait in applicant_joblinks
    with materialized = 0.
 3. CAM "Assignments" tab (GET /api/cam/pool) shows the pool + live
    quota (assigned/quota). CAM picks a CA -> POST /api/cam/assign
    -> assignApplicantToCa() enforces the quota, sets ca_id/cam_id,
    and materializeJoblinks() turns each pending link into an
    ASSIGNED application in that CA's queue.
 4. CA clicks APPLY -> application ASSIGNED -> QUEUED, and
    worker.kick() runs immediately (no poll wait).

PARALLELISM MODEL (the core of the request)
 worker/runner.js keeps a poll loop (WORKER_POLL_MS) that is a
 backstop; the real trigger is server.js calling worker.kick() on
 every APPLY. tick() claims up to (MAX_CONCURRENT - active) QUEUED
 rows and, for EACH, spawn()s an independent child:
     node ashby-hybrid-automation.js <url> <resume> 
       env APPLICANT_ID / PERSON_PROFILE_PATH / APPLICANT_DB_PATH /
           APPLICANT_DATA_DIR=<own run dir>
 N children = N browsers at once, each with its own applicant-data
 folder, so there is NO shared state and NO ordering. claimForRun()
 flips QUEUED -> APPLYING atomically (guarded UPDATE) so two slots
 can never grab the same row. QUEUED rows past the cap simply wait
 for the next free slot and are still picked up live. On child close
 readLatestResult() scans the run's jobs/*.json and finishRun() maps
 success->SUCCESS, failed->FAILED (banner reason), unknown/manual-
 review/pending->PENDING, crash/no-result->FAILED; the downloaded
 resume is then deleted.

NEW SCHEMA (idempotent ALTERs in db/index.js migrate())
 staff: applicant_quota (default 25, the per-CAM cap), ext_id
 applicants: cam_id, ext_id, assigned_at (ca_id now set by CAM)
 new table applicant_joblinks (awl_id,url,company,title,materialized)
 applications: resolution_log_json

NEW / CHANGED ROUTES (server.js)

 POST /api/cam/assign          attach applicant to a CA (quota-checked)
 POST /api/dev/sync            pull applicants+links from Postgres

 POST /api/dev/staff/:uuid/quota   set a CAM's applicant quota
 POST /api/dev/worker            enable/disable the runner (was toggle)
 APPLY route now also calls worker.kick()

NEW UI (public/js/app.js)

 DEV -> "Data Sync" tab (Sync from Postgres, Ingest JSON, per-CAM
          quota inputs, worker enable/disable with live active count)

CONFIG (.env.example in dashboards folder)

 PG_CONNECTION_STRING or PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/

11. v3.3 - BROWSER CAPABILITY GATE (no host claims what it cannot finish)
====================================================================
THE INCIDENT THIS EXISTS FOR
  Five links were ingested and every one "failed" in ~9s with "No
  scan output produced (engine exit code 1)"; two applicants then
  went FAILED with "Engine process exited without a result". The
  links and the applicants were fine. The real line, buried under
  the wrapper, was
     browserType.launch: Executable doesn't exist at
     /root/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome
  i.e. a MACHINE was missing a browser and the damage was filed
  against other people's data. Three separate defects let that
  happen, and all three are now closed structurally:
  (a) the queue lives in SHARED Postgres, so the browserless
      Railway container claimed real work it could never finish;
  (b) nothing ever installed a browser - root package.json's
      postinstall only installs dashboard deps, so a deployed
      host has the playwright LIBRARY and no binary;
  (c) a listing/404 page can be "scanned" into a 1-field junk
      inventory, which is then published to the shared cache and
      served as the truth to every later applicant everywhere.

WHAT  core/browser-probe.js + core/browser-check.js
HOW   the probe is a child process, run ONCE PER MODE (argv 'apply' or
      'scan'), that mirrors the ENGINE's own search for a binary
      (CHROME_PATH -> installed Chrome on Windows
      -> Playwright's bundled Chromium) and that mode's own launch -
      HEADED for applies unless APPLY_HEADLESS/HEADLESS=true, headless for
      scans unless SCAN_HEADLESS=false, --start-maximized and all. It opens
      about:blank and closes. It answers on ONE tab-separated
      stdout line prefixed BROWSER_PROBE (tabs because Windows
      paths contain spaces; the prefix because dotenv prints an
      "injected env" banner on the same stdout), tagged
      OK / MISSING / NOLOAD / NOEXEC / LAUNCHFAIL. browser-check.js
      caches that verdict per mode, loads .env for the child, and
      never touches the network.
WHY   existsSync() is not the truth: the incident was exactly
      "the host looked capable and was not", and the next variant
      (no libnss3, no /dev/shm, read-only FS) would pass a file
      check too. Launching is the only honest answer. Mirroring the
      engine's order matters the other way: probe only the bundled
      Chromium and a laptop with real Chrome is pinned off forever.
      NOT awaited at boot (server.js fires it and moves on) because
      a first launch can take tens of seconds and HTTP cannot wait;
      until it answers every tick declines to claim, which is the
      safe direction. Fail-closed by default.

THE GATE IN THE TWO WORKERS
  apply worker (worker/runner.js): will not claim a run without a
  proven browser.
  scan worker (worker/link-scanner.js): cache tiers need no browser,
  so a browserless host still answers a link the shared/local cache
  already knows; if a real page load is required it exits 3
  (NEEDS_BROWSER) and the row is DEFERRED - attempt REFUNDED, back
  to PENDING, next_attempt_at = now + SCAN_DEFER_MS (default 5m) -
  so a link cannot be killed by being parked on the wrong machine.
  A "Scan refused" is the LINK's fault, not the host's: attempts are
  maxed so it parks FAILED at once instead of burning retries.
  Host fault vs applicant fault: an apply run that dies on a missing
  browser is handed back (handBackToQueue: APPLYING -> QUEUED, the
  machine's error is NOT stored as the applicant's fail_reason, a
  application.handback event is logged). SUCCESS is never re-opened.

  v3.3a - THE GATE HAD THE SAME BUG IT WAS WRITTEN TO CATCH
  The first version launched ONE probe, headless, and shared its answer
  between both workers. It went live, called itself ready on Railway, and
  destroyed the two applications it was meant to protect - because the
  engine does not apply headless: line ~647 launches HEADED unless
  APPLY_HEADLESS/HEADLESS=true (a real window is the best signal available
  to Ashby's anti-spam filter), while the scan path (line ~805) is headless
  by default. On a container with no display those are two different
  questions with two different answers, and the headed one fails with
     browserType.launch: Target page, context or browser has been closed
  Worse, the hand-back put the row straight back into a QUEUED pool that the
  same host re-claimed on the next poll tick: 56 claim/launch/hand-back
  cycles in eight minutes on one AWL-ID, 62 attempts on each application and
  ~580 event rows, none of which was ever the applicant's fault.
  Both halves are now structural:
   • TWO VERDICTS. The probe takes its mode from argv ('apply' | 'scan',
     unknown = 'apply', the destructive default) and mirrors that mode's
     headless flag AND its launch args (--start-maximized included, since
     that is exactly what a headless-only probe never exercises). browser-
     check.js caches one state per mode; browserState(mode) /
     canDriveBrowsers(mode) / checkBrowser({mode}) are the API, and 'apply'
     is the default so a call site that forgets to say gets the STRICTER
     answer. The apply worker gates on 'apply', the scan worker on 'scan',
     and server.js measures both at boot (sequentially - two cold browser
     launches on a small host compete for memory). A display-less container
     is a legitimate SCANNER either way, and what it may do as an APPLICATOR
     is decided by v3.3b below - which is exactly the point of the split,
     since the two modes used to be reported as one answer.
   • A HANDBACK IS A PAUSE, NOT A RE-QUEUE. applications.next_attempt_at
     (both schemas + idempotent ALTER) is set to now + APPLY_DEFER_MS
     (default 5m) by handBackToQueue, filtered out of listQueuedForWorker()
     AND refused by the atomic claim in claimForRun() itself (a poll that
     read the row before the pause existed must still lose the race).
     applyApplication() and devRequeue() clear it: a human clicking APPLY or
     Retry means NOW. NULL means due, so nothing about a normal run changes.
  What this means operationally: a display-less host serves the API, the
  shared cache and headless scans, and an apply run goes to whatever mode
  this host's rule resolves to - see v3.3b. The queue waits; it no longer
  burns.

v3.3b - ONE RULE FOR HOW AN APPLY LAUNCHES (core/apply-mode.js)
  Splitting the verdict only made Railway honest about something it had been
  doing all along: it could not apply at all, because headed is the engine's
  default and a container has no display to honour it. The operator's
  decision was that Railway applies headlessly. The naive way to get that is
  to set APPLY_HEADLESS=true in the Railway variables - which works until the
  next host, or a rebuild that lost the variable, quietly returns the
  platform to this same half-broken state. So it is a rule, not a setting:

    explicit APPLY_HEADLESS / HEADLESS  -> exactly that, in BOTH directions
    nothing set + linux with no DISPLAY and no WAYLAND_DISPLAY -> headless
    anything else (windows, macOS, a box running xvfb)         -> headed

  Three properties are what make it stop coming back:
   • the engine is STILL untouched (standing rule). worker/runner.js
     resolves the mode once at boot and passes APPLY_HEADLESS=<the answer>
     in the child's environment - the variable the engine already reads.
     Nothing can end up half headless, because probe, worker and child take
     the value from one call.
   • the probe asks the SAME rule, so it launches in the mode the run will
     use. A container that auto-selected headless is measured headless and
     passes; a container an operator forced to APPLY_HEADLESS=false is
     measured headed, fails, pins itself off and leaves the applications
     queued. The false READY that started this repair can no longer be told
     from inside the gate.
   • the DEV pane says WHY ("no display on this linux host" as against
     "configured"), because an automatic decision that looks like a silent
     override is the next bug report.
  The cost, stated plainly: a headless apply from a datacenter IP is a
  weaker anti-bot signal than the window on a residential laptop - the
  engine's own comment calls headless "a throughput tradeoff, not a free
  win", and its stealth wiring does not mask the IP. Both hosts now claim
  from one shared queue, so either can take a row. Where one submission
  matters more than throughput, set APPLY_HEADLESS=false with xvfb on that
  host (or WORKER_ENABLED=false to keep it off applies entirely) and the gate
  will measure that mode honestly instead of faking a READY.

v3.3c - THE HOST'S BUDGET, AND WHO PAYS FOR A DEATH
  With the gate in place Railway went and DID apply: one tick claimed three
  applications (Drata, Render, FutureFit) and launched three Chromiums at once.
  Two submitted normally after ~90 seconds, screenshots and all. The third died
  six seconds in - no result JSON, no screenshot, nothing printed - and was
  filed as the applicant's FAILED application with the placeholder reason
  "Engine process exited without a result". Nothing had been submitted and
  nothing had been judged: the kernel ran out of memory and chose a victim, and
  the applicant wore the machine's problem as a rejection. Same bug class as the
  missing binary, second flavour, found because the deploy was finally able to
  run. Two rules close it:
   • COUNT BROWSERS AGAINST REAL MEMORY (core/host-capacity.js). Capacity is
     bytes available / 512MB per browser (APPLY_BROWSER_MB to change), where
     "available" is read from the cgroup limit first - os.totalmem() inside a
     container reports the HOST NODE, so a 512MB service on an 8GB machine
     would otherwise be told it can run sixteen browsers - falling back to
     os.totalmem() on a normal laptop. MAX_CONCURRENT_RUNS stays the operator's
     CEILING and is now clamped by it; "unlimited" means "as many as fit", never
     an infinite number; capacity is never below 1 so a tiny host still works,
     just one at a time. The scanner takes at most half the budget (a scan that
     waits costs minutes and is refunded/deferred; an apply that dies costs a
     person), and both numbers plus the reason are in the DEV pane. Overrides:
     MAX_BROWSERS, HOST_MEM_MB, APPLY_BROWSER_MB.
   • A DEATH WITH NO EVIDENCE IS A HOST FAULT (core/host-fault.js, pure and
     asserted). An application may only be FAILED on evidence the FORM was
     reached: the engine wrote a result, or it printed its own error. So the
     browser-signature rule, "killed by a signal / exit 137-143 with no result"
     and "exited without a result or any output at all" all hand the row back
     to the queue, parked for APPLY_DEFER_MS and retried, while a run that
     reached the page keeps its banner. A SUCCESS never hands back. When a real
     run leaves no result but did print something, that last line is now the
     recorded reason instead of the placeholder - #62 was undiagnosable for
     exactly this reason, and the exit code/signal/concurrent-count/capacity are
     logged on the hand-back event so the next one explains itself.
  Residual, stated: the two workers are capped by the same budget separately, so
  1 apply + 1 scan can still be two Chromiums on a one-browser host. The
  estimate is deliberately conservative and the classifier is the backstop - a
  death without evidence costs a wait, not an applicant.

v3.3d - WHAT ASHBY ACTUALLY SAID (core/submission-banner.js)
  Those same three Railway runs also answered the question "so why did only one
  go through": two of them came back with Ashby's red "We couldn't submit your
  application - Your application submission was flagged as possible spam" box
  (the operator's screenshots of Render and mdCalc), one with the green
  Success box (FutureFit). Nothing in the platform said so. The engine only
  recognises two acknowledgements - success and missing-fields - and stores
  every other page as 'unknown' TOGETHER WITH the visible page text, which the
  worker then dropped on the floor: the run was filed PENDING "Outcome
  unclear" and finishRun() nulled fail_reason for anything that was not a
  failure, so the row showed no explanation at all and a human had to open a
  screenshot to learn what the page had already said in words.
  Three changes, none of them in the engine:
   - core/submission-banner.js reads an unclear post-submit page's own banner
     and names the outcome ("flagged as possible spam - NOT submitted ... this
     host's network is what Ashby distrusted"), quoting at most 160 characters
     of it. An unrecognised page stays "Outcome unclear": guessing that a
     submission worked is worse than admitting we cannot read it.
   - worker/runner.js applies it to the 'unknown' branch only, so a spam-flagged
     run stays PENDING for a human (never SUCCESS, never the applicant's
     FAILED) and is logged as run_spam_flagged rather than run_pending. It is
     deliberately NOT re-queued by machine: a retry from the same IP gets
     flagged again and teaches Ashby to distrust that address harder.
   - db/store.js finishRun() now keeps the reason on a PENDING row.
  Also fixed on the way: RUN_START_SPACING_MS was switched off exactly when it
  was needed - the ternary was inverted against its own comment, so an
  UNLIMITED worker launched the entire queue inside one second (three
  simultaneous identical submissions from one datacenter IP is precisely the
  shape that gets flagged). Starts are now staggered on every host, capped or
  not, and the comment says what that is for: memory and shape, not
  deliverability. No amount of spacing makes a datacenter IP look residential.

v3.4 - "THE CRM HAS HER, THIS HOST CANNOT SEE HER" (core/applicant-source.js)
  AWL-25663 is the proof that 'Resume unavailable: no resume address' was a lie.

   - the apply worker then found profile_json '{}' and called

  So one host that cannot read the CRM did two things badly: it stored a

  ('AWL-25663') -> {seen:1, updated:1} -> real name/email/phone, resume set
  (109 chars, http), 34-column raw profile. Run #101 was deliberately left
  FAILED - the CA's APPLY click is the consent, so one Retry click re-queues it

  Residual, stated: the fix makes a connector-less host honest, not capable.
  Railway still needs PGHOST/PGUSER/PGPASSWORD/PGDATABASE to ingest or apply

v3.4a - WHICH VARIABLE NAME COUNTS AS A CRM CONNECTOR (one list)
  The operator had in fact given Railway database credentials, which made the
  sentence above wrong as written - so the question became which name the code
  accepts. It accepted exactly two: pgConfig() in connector/azure-config.js
  checked PGHOST || AZURE_PG_HOST and returned null otherwise, while
  connector/applicant-db.js's own error message promised that
  PG_CONNECTION_STRING alone would do, and the v3.4 classifier (written from
  that message) agreed with the message rather than the pool builder. A host
  handed ONE connection URL - which is what a managed-Postgres dashboard
  generates, Railway included - was therefore 'configured' in two places and
  unable to connect in the third, and every symptom downstream looked like a
  missing applicant.
  Now the list exists once, in core/applicant-source.js:
   - CRM_HOST_NAMES (PGHOST, AZURE_PG_HOST) and CRM_URL_NAMES
     (PG_CONNECTION_STRING, AZURE_PG_URL, AZURE_DB_URL, CRM_DB_URL,
     CRM_DATABASE_URL). azure-config.js imports both and builds the pool from
     them: a URL-only host gets {connectionString, ssl} with NO empty host/user
     keys, because pg lets explicit config override the values parsed out of
     the URL, and `host: ''` would have silently wrecked a working string.
   - DATABASE_URL / POSTGRES_URL are deliberately NOT accepted. On Railway and
     Supabase those names are the PLATFORM's own database; reading
     client_profiles from them fails with 'relation does not exist' while
     pretending the CRM was reachable. verify:flow asserts they stay out.
   - describeConnectorEnv() reports which names ARRIVED on a host, names only.
     The DEV 'Applicant DB connector' card now shows the answering host, the
     names it looks for, the ones it got, and a red warning when it got none -
     because an operator cannot shell into a container to check.
     server.js also stopped claiming 'OK (local SQLite)' unconditionally: it
     reports the real backend and hostname.
   - worker/runner.js run_started now carries host + crm_connector +
     has_resume. Both of this session's incidents (the AWL-25663 placeholder and
     the 09:59 no_postgres writeback) had to be reconstructed from which events
     were ABSENT; a run should say who ran it and what that machine could see in
     its first line, not its last.
  Proof the heal did land, through the join the worker actually uses

15. v3.6b - WHY A RUN GETS FLAGGED, AND NEVER ASK THE CA TWICE
====================================================================
An operator submitted the SAME applicant by hand (accepted) and via the
automation on Railway (rejected with Ashby's red "flagged as possible spam"
banner). Identical form data, opposite outcome. The difference is the NETWORK
ORIGIN, not the answers and not the five end-user tips Ashby prints (VPN,
extensions, browser, network, wait) - none of which applied here. Railway is a
datacenter IP; Ashby's anti-abuse layer distrusts datacenter traffic and/or
several rapid submissions from one IP, so it flags the SUBMIT, not the person.
The engine saw neither a success nor a missing-fields banner, stored the run as
'unknown' WITH the page text, and the runner's readUnknownBanner named it 'spam'
-> left PENDING for a human and NOT retried from the same bad host (that would
only deepen the IP's reputation hit). This is the documented v3.3d reality: where
deliverability matters, apply from a residential host (WORKER_ENABLED=false on
the container). It is an operational fact, not a code bug - the platform already
correctly refuses to burn the applicant by hammering a distrusted IP.

The evidence screenshot for the filled form is captured by the ENGINE with
page.screenshot({ fullPage: true }); Ashby's sticky header re-paints during
Chromium's full-page scroll-and-stitch, so the shot can show the logo overlapping
mid-page. Fixing that means editing ashby-hybrid-automation.js, which is
off-limits by standing rule - flagged, not changed.

THREE RULE FIXES landed here (all asserted in verify:flow, none a setting):
  * A URL / link box is NEVER filled with "N/A". "N/A" is not a valid URL and
    Ashby rejects it ("Please enter a valid URL") - it was a real submission
    killer. An optional link box with nothing to source now stays blank.
  * Before a field is escalated to the CA, the applicant's OWN resume is mined
    model-free for a confident shape match (email / phone / link only). The CRM
    record already had its chance in Tiers 1-2.5; the resume is the second
    source, and because it needs no API it keeps filling values through a
    GenAI quota outage (429). Ambiguous questions still go to the CA - it can
    never invent an answer.
  * A hung run can no longer hold a browser slot: a RUN_TIMEOUT_MS watchdog
    (default 6 min) kills the child, so finish() files whatever result exists

    idle. An empty queue already idles (the poll launches nothing); this closes
    the other half - a stuck child never keeps the machine busy.

verify:flow (step 3d) asserts the URL guard, the model-free resume extraction

20. v3.7 - CA WORK-HISTORY + ca_data (DYNAMIC EXTERNAL APIs, VISIBILITY-ONLY)
====================================================================
The operator asked: persist the AWL -> CA -> OM(CAM) map so a CA's whole book
shows under them, let OMs + DEV read each CA's day-to-day work over a from/to
span, and keep the external endpoint configuration editable by DEV/ADMIN only,
dynamically - never hardcoded, never in .env.

  * THE INDEX (ca_data, both backends): one row per AWL-ID -> { ca_id, ca_email,
    ca_ext_id, om_id, om_email, om_ext_id }, built purely from the CRM's
    clients_additional_info (career_associate_id / career_associate_manager_id)
    matched onto staff by ext_id. connector/ca-data.js buildCaData().

  * THE EMAIL BRIDGE: ca_email resolves from the roster FIRST (staff.ext_id ->
    staff.email); when the CRM names a CA uuid with NO staff row it falls back to
    the external /api/ca/emails id->email map and records the email while leaving
    ca_id NULL. We NEVER invent a person - an id absent from BOTH roster and the
    emails feed stays unresolved and surfaced (e.g. 4f3b6068 / AWL-35186).

  * VISIBILITY-ONLY ASSIGNMENT (the anti-flood rule): a refresh points every
    applicant at its real CA/OM (applicants.ca_id/ops_id) so each CA sees their
    clients, but it must NOT auto-create applications or a scan backlog. That is
    enforced by a materialize switch threaded through db/store.js
    upsertExternalApplicant + upsertApplicantJoblink (and connector/applicant-db.js
    upsertCombined/syncFromPostgres): default true (every existing caller
    unchanged), set false by the refresh so links land PENDING (materialized=0)
    and no job_links/applications rows are written. verify proves both halves -
    materialize:false adds a pending link and creates nothing; materialize:true
    (the control) materialises exactly one.

  * THE NUMBERS come from the external work-history API (full org activity,
    including work this platform did not do), cached into ca_work_history keyed
    (work_date, awl_id, ca_email) by connector/work-history.js

    A CA "worked" in a span = they have cached rows in it. getCaWorkHistory /
    getCaWorkHistoryDetail read the cache over an inclusive [from,to]; the
    innermost per-link detail re-attaches our own applications when that AWL+link
